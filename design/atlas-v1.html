Deck/ Screen/ All agents

Atlas — v1

3 variants + 1 separate decision · 6 real agents · 5 projects

Today Atlas.jsx is a grid of cards sorted by recent activity. With six sessions across five projects talking to each other, that grid has three defects: position means nothing (it reshuffles on its own, no muscle memory), the project isn't visible, and communication isn't there — it lives in Room, which is pairwise.

The three variants below are live: a simulator is emitting messages so you can judge them moving. All three share four rules: color is status and project is position (five accessible hues over #0c0e11 don't exist — palette.js only validates three); a message travels in ink, not in a status hue, so it doesn't read as "busy"; nothing is inferred — a message with no recorded delivery is drawn truncated and open; and zero dependencies: SVG, transform and requestAnimationFrame, the same thing FileMap.jsx already does.

⚠
What's real and what isn't. The six agents —name, project and status— come from ~/.claude/sessions on 24 Sep 2026 at 22:30. The messages between them are invented: these sessions haven't talked to each other yet. It's the only fictional thing on the page.

A · Score proposal

One lane per agent, grouped by project with a brace on the left. Time runs left to right and "now" is the right edge: everything slides into the past on its own. The lane beats: writes upward, reads downward — density, not identity, which is what survives sixty files. A message is an arc leaving the lane of whoever speaks and landing in the lane of whoever listens; the horizontal is real time, so one read instantly comes out nearly vertical and one that sat four minutes in the queue comes out flat. The arc doesn't exaggerate latency: it shows it at the scale where it matters.

Arc = a message, crossing Flat arc = took a while to be read Open end = no recorded delivery Up = writes · down = reads Red = a tool failed Brace = project

Position is stable. The order is project and then name, never activity: the row you were watching is still where it was ten minutes from now.

It answers both questions at once — what each one is doing (its trace) and what they're saying (the arcs) — without switching screens.

Time is real. A long gap looks like a long gap; a fast ping-pong looks tight. And delivery latency reads without reading a single number.

It scales. Twelve agents are twelve 34 px rows. Try it with the toggle.

You only see the window. Ten minutes; anything before that is gone. It needs a zoom or a "see the whole session" the mockup doesn't draw.

The "where" is reduced to a folder. The trace says how much and of what kind; per-file detail moves to the session view. See section D — it's a deliberate loss, but it's a loss.

The arcs cross when non-adjacent lanes talk. Six holds up; at twenty you'd have to kill old arcs sooner.

Only one message is labeled at a time. With three in flight the captions collide, so the most recent gets the label and the rest stay as arcs. Everything else is a hover away.

B · Constellation alternative

Each agent is a node; those from the same project form a cluster. Lines exist only between pairs that have actually talked, and their thickness is how many times. When a message goes out, a dot of ink runs along it. The node's halo beats while it works.

topology, not chronology
Line = they've talked Thickness = how many times Dot = message in flight Halo = working Cluster = project

The topology jumps out in a second: who's the hub, who talks to everyone, who's isolated.

Deterministic positions. No physics: the cluster is computed from the project, so it doesn't jitter or reorder between polls.

It's the one that reads best from a distance, on a monitor off to the side, without reading.

There's no time. You see that they talk, not when or in what order. For supervising, "when" is usually the question.

A node fits very little text. You lose path, counters and detailed status; all of it moves to hover.

With two agents it's ridiculous and with fifteen it's a tangle. The useful window is narrow.

It's the prettiest and the least answering. That is exactly the risk.

C · Live grid minimum change

Today's cards, but sorted by project and frozen (no more reshuffling), with wires drawn on top when a message flies. The receiving card lights up.

Wire = message in flight Light border = just received Bars = files per minute Order = project, fixed

It's the cheapest change. It keeps the file map, the counters and all the CSS that already exists.

It fixes the worst defect for free — the reshuffling — just by changing the sort criterion.

Every card stays clickable and dense. Nothing is lost.

The wire measures nothing. Its length is where the cards happened to land in the grid, not latency or real distance. It's decoration pretending to be data.

The message only exists while it flies. If you weren't looking, it didn't happen: no trace is left.

When the grid wraps, the wires cross the whole screen and turn into noise.

D · What to do with the file map separate decision

Today's FileMap is a treemap: one rectangle per file, grouped by folder. It works with fifteen files and falls apart at sixty, which is the normal case ten minutes into the work. The failure isn't about size, it's about the question: the treemap answers "which one?" by drawing identities, and on the all-agents screen the question is never "which one?" — it's "is it still moving, and is it reading or changing things?". Three ways to answer it, from most to least information per pixel.

Same data in all three: 58 files, 9 writes, 1 failure Same width: 260 px

D2 is the proposal — the two-sided beat. It scales without limit because it doesn't draw files, it draws density: sixty and six hundred look equally good.

It separates the one thing that decides whether you need to look. Reading is cheap and breaks nothing; writing does. Today both are the same gray rectangle.

It leaves room for failure. A full-height red mark is visible from across the desk, and --critical is reserved for exactly this.

And it recovers the cheap "where": one line of text with the hot folder (bicep/modules/) says more than sixty unlabeled rectangles, and it never degrades.

D1 (today's treemap) isn't thrown out, it moves. Inside a session, with a single session to look at, it does answer "which one?" and that's where it belongs.

D3 (sparkline) is too little. It fits anywhere and doesn't tell reading from writing, which is exactly the distinction needed. It works for a sidebar row, not for this screen.

"Hot folder" needs a rule. With the work split evenly across three folders, picking one lies. The honest rule is to show it only if it's over 40 % of the last minute's events, and otherwise show nothing.

Verdict — A, with C as a first step

A (Score) is the proposal. It's the only one of the three where the geometry is data: the vertical is who, the horizontal is when, the arc's length is delivery latency and the open end is the absence of an acknowledgment. The other two animate on top of arbitrary positions — pretty, but the movement doesn't inform.

B (Constellation) isn't discarded, it's subordinated: it's a good second mode for the same screen ("topology" next to "chronology"), and it shares the whole data model. It doesn't deserve to be the default view because it doesn't answer "when", which is the supervisor's question.

C (Live grid) contains one improvement worth taking even if A wins: sort by project and stop reshuffling. That's three lines in Atlas.jsx and it can be done today.

D is a decision independent of the three: the per-file treemap falls apart at sixty files and it falls apart because it answers the wrong question for this screen. Swapping it for the two-sided beat —writes up, reads down, failure in red— plus one line with the hot folder improves all three variants equally, including today's grid if nothing else ends up changing. The treemap isn't thrown out: it stays inside the session view, which is where "which file?" is the question.

None of this needs new data. The lanes and the traces come from /api/activity, which already exists; the arcs come from /api/meetings (src/meeting.js), which already returns from, to, at, deliveredAt, summary and hops — exactly the five fields A draws. The one missing piece is an aggregate endpoint: today Room serves conversations by pair and this screen wants every turn from the last N minutes in a single response.
