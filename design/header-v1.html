Three ways to win the screen back

All three fit in model and effort. What changes is where the things you read live — path, branch, context, time — against the things you touch.

What else deserves a button — and what does not

This is not a wish list: it is what the session really exposes live, read from the SDK types. What is not there cannot be offered without making it up.

● Model

Changes live, without throwing away the turn in flight. The session itself gives the list, with a name and a description for each one.

setModel() · supportedModels()

● Effort

Also live. The levels depend on the model, so the list is rewritten when you change it.

applyFlagSettings({ effortLevel })

● This session's commands

Which /commands and skills it has loaded. Today you type them blind and you do not know which ones exist here. I would put it in the composer, not in the header: you use it by typing.

supportedCommands()

● The available subagents

Which agents this session can launch, with their description. It is reading, not acting: it fits better in the Agents tab that already exists.

supportedAgents()

● MCP status

Which ones connected and which ones are asking for authentication. There is already an MCP screen in Settings; in the header it would only be worth it as a warning when one fails.

mcpServerStatus()

● Token budget for the turn

It sounds useful and I would not add it: the context meter already says the only actionable thing, and a second number in the same header competes with it without adding a decision you can make.

—

What I would implement

  1. One row for what you touch, one thin line for what you read. Name and tabs on top; path, branch, context, model, effort, permissions and Kill in a 26 px strip. From 172 px down to ~70.
  2. The session answers the model list, not the browser. supportedModels() returns the name, the description and the effort levels of each one. A hand-written dropdown ages the day a model ships.
  3. Picking a model rewrites the effort list. Not all of them take the five levels; offering one the model does not have is promising what will not be kept.
  4. Asking is not getting, and it says so. max is session-only and runs as high on a model without support; an organization can also cap the level. The chip shows what was granted and warns in amber when it is not what you asked for — the same rule the deck already applies to the permission mode.
  5. The permissions warning stops being a band. It is the same sentence the chip is already saying in amber; as a band it costs 40 permanent px.
